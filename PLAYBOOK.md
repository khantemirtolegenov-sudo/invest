# Плейбук: как строить внутренний портал из шаблона

> Переработанная карта пути ColliersHUB (июнь–ноябрь 2026: 731 коммит, ~40 инструментов,
> 96 миграций) — не как было, а **как должно быть**. Каждый этап: цель, что делаем, как
> понять, что этап закончен, и какие ошибки прародителя он закрывает. В конце — куда
> вписывать новую идею и ежедневный ритм работы с Claude.

## Главная мысль

В ColliersHUB скорость упиралась не в написание кода, а в три вещи: **переделки по
неясной задаче**, **тихие ошибки** (интерфейс говорит «готово», а данных нет) и **ручную
выкладку вслепую**. Шаблон уже закрывает фундамент; плейбук закрывает процесс.

| Было в ColliersHUB | Как теперь |
| :--- | :--- |
| Фундамент (данные, права, синк, деплой) — весь первый месяц | `npm run setup` — день |
| Каждый инструмент: 4 места регистрации руками, ошибки прав | `npm run new-tool` — минута, права сразу на обеих сторонах |
| Ответы на опросы терялись 3 месяца (неверное поле владельца) | сторож `check:acl` в сборке + журнал отказов + `confirmSync` |
| Правки пропадали при F5 и выкладке | ящик неотправленного с первого дня |
| Поломки видели на проде | CI на каждый пуш: права, типы, сборка, backend на чистой базе, Docker |
| Задачу начинали писать, потом отменяли (kino.kz → sxodim → отмена) | бриф из 5 пунктов + проверка внешнего источника до кода |
| Встраивание чужого HTML «окном», потом перенос | живой инструмент — сразу родной страницей |
| CLAUDE.md разросся до 250 КБ и съедал контекст | CLAUDE.md — только правила; история — `docs/tools/` |
| Один бесконечный чат на всё | новая сессия на задачу; параллельно — 2–3 сессии в своих ветках |

## Этап 0. Идея и бриф (час)

**Цель:** понять процесс, который портал ускоряет, прежде чем писать код.

1. Какой процесс? Кто в нём участвует (роли), что сейчас делают руками (Excel, чаты, почта)?
2. Какие 3 действия делаются чаще всего — с них и начинаем.
3. Где люди работают физически: офис, разъезды, телефон? (в прародителе Telegram оказался
   главным каналом, потому что портал был доступен только из офисной сети).
4. Кто администратор, кто выдаёт доступы, кто выкладывает.

**Готово, когда:** есть одна страница «процесс → роли → 3 первых инструмента → доступы».

## Этап 1. Старт из шаблона (день)

`npm run setup` (или «начинаем» в Claude Code — он задаст вопросы сам): название, модули,
администратор, первые инструменты. Затем `npm run install:all`, база, `db:seed`, `dev`.
Сразу: создать репозиторий, подключить CI (модуль `ci`), договориться, кто и как выкладывает.

**Готово, когда:** портал открывается, админ входит, CI зелёный, есть сервер для выкладки.

## Этап 2. Первый инструмент от начала до конца (1–3 дня)

Не «всё понемногу», а **один** инструмент полностью: генератор → предметная логика →
три состояния экрана → права проверены запросом (403) → живой прогон → выкладка.
Это калибрует весь конвейер: если на первом инструменте что-то неудобно, чините процесс,
а не обходите его.

**Готово, когда:** 3–5 реальных людей пользуются инструментом на проде неделю.

## Этап 3. Пилот и связь с людьми (неделя)

- Уведомления: всё важное — через `notify()`; модуль `telegram` — если люди не у компьютера.
- Один трекер мелких правок от владельца (Notion/таблица): правки копятся и закрываются
  пачками, а не по одной посреди другой работы.
- Журнал отказов (`sync_rejections`) смотреть раз в день первые две недели.

**Готово, когда:** правки пилотной группы идут через трекер, отказов прав нет.

## Этап 4. Конвейер инструментов (основное время проекта)

Каждый инструмент — по одному рецепту:
1. **Бриф** (5 пунктов) → 2. `npm run new-tool` → 3. предметная логика в модуле и экране →
4. особые правила записи в `checkWrite`, если нужны → 5. `verifier` (+ `acl-guard`, если
трогали доступ) → 6. `docs-keeper` → 7. коммит в ветку → 8. «мердж и пуш» владельца → выкладка.

Параллельно можно вести 2–3 инструмента в разных сессиях и ветках: сервисный слой разбит
по файлам, конфликтов почти нет. Делить работу между агентами **по фичам, а не по слоям**
(«агент фронтенда» и «агент бэкенда» рассинхронизируют права — ровно класс ошибок, который
стоил прародителю дороже всего).

## Этап 5. Внешние данные и ИИ (по мере надобности)

- Тяжёлое и чужое (парсеры, генерация документов, статистика) — **отдельным сервисом за
  прокси портала** с белым списком путей; портал проверяет права, сервис делает работу.
- ИИ получает **только посчитанные факты**; текст с числом, которого нет в фактах, отбрасывается;
  сохраняет всегда человек кнопкой. Людей и контакты ИИ не выдумывает.
- Бесплатные модели — с кешем, частями, ожиданием лимита и запасной моделью.
- Документы (PowerPoint, Word) собирает код по правилам, а не модель «сделай презентацию».

## Этап 6. Эксплуатация (постоянно)

- Сигнал «портал упал» в Telegram (проверка `/api/health` раз в минуту).
- Бэкап базы по расписанию (`npm run backup:db`) и проверка восстановления раз в квартал.
- Новые миграции перед выкладкой — бэкап; необратимые (удаление колонок) — отдельным шагом.
- Раз в месяц: какие инструменты не открывают (мёртвые — на удаление), что просят чаще всего.

## Новая идея — куда она вписывается

| Идея | Этап | Что делать |
| :--- | :--- | :--- |
| Новый раздел со своими данными (реестр, заявки, учёт) | 4 | бриф → `npm run new-tool` |
| Поле или кнопка в существующем инструменте | 4 | правка модуля и экрана; смена формы данных — новой миграцией |
| Кто-то должен узнавать о событии | 3 | `notify()` в методе; вне портала — модуль telegram |
| Данные из внешней системы (CRM, сайт, API) | 5 | сначала проверить доступность и формат; отдельный сервис за прокси или снимок |
| «Пусть ИИ пишет / разбирает» | 5 | только по фактам, с проверкой ответа и подтверждением человеком |
| Документ или презентация по данным портала | 5 | генерация кодом по правилам + проверка; модель — только текст выводов |
| Кому-то нужен доступ / закрыть доступ | 4 | грант в «Пользователях»; новое правило — обе стороны + 403 запросом |
| Портал тормозит или падает | 6 | логи, health, журнал отказов; не чинить вслепую — сначала доступ к логам |
| Похоже на отдельный продукт со своими пользователями | 0 | новый проект из шаблона, а не ещё одна вкладка |

## Работа с Claude: ежедневный ритм

1. **Одна задача — одна сессия.** CLAUDE.md лёгкий, подробности — в `docs/tools/`, поэтому
   новая сессия дешёвая. Длинный чат на всё подряд теряет детали при сжатии.
2. **Начало задачи — бриф.** Claude сам спросит недостающее (правило в CLAUDE.md).
3. **Шаблонный код — генератором**, модель пишет только смысл.
4. **Проверка — агентами**: `verifier` перед коммитом, `acl-guard` при изменении доступа,
   `docs-keeper` для документации. Они на дешёвой модели и читают только своё.
5. **Тестовый админ для проверки интерфейса**: учётка из сида на локальной базе, чтобы
   Claude сам проходил изменённый сценарий в браузере, а не писал «не проверено».
6. **Пуш и выкладка — решение владельца.** Claude коммитит и мержит, выкладывает человек
   («мердж и пуш»).
7. **Каждый повторившийся промах — в правило** CLAUDE.md (раздел «Конвенции» или «Планка
   качества»). Так прародитель вырастил таблицу «типичные ошибки → правило».

## Чего не делать

- Не держать историю решений в CLAUDE.md — только в `docs/`.
- Не создавать «агента на каждый инструмент» и «агента-программиста» — работа идёт в основной сессии.
- Не встраивать живые инструменты чужим HTML в рамке — потом всё равно переносить.
- Не проверять права только в интерфейсе.
- Не говорить человеку «готово», пока сервер не принял (`confirmSync`).
- Не начинать код по внешнему сайту, не проверив, что он доступен с сервера.
